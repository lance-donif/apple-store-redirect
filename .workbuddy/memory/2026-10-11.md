# 2026-10-11

## 用户反馈「失效」排查：确认两个真实缺陷并修复

单测与浏览器测试**最初都是全绿的**，但真实用户场景确实失效。两处根因都属于「测试假环境掩盖真实运行时」类型。

### 缺陷 1：guard.js 的 pendingAppUrl 全局劫持（主因，用户可见失效）

`guarded()` 原先无条件用 `pendingAppUrl` 作为所有 `/cn/` 跳转的目标。该字段本意只是「Apple 弹回 /cn/ 时还原原 App 页」，却在每次访问 App 页时被写入，于是变成全局劫持器：

- 在 App 页 `pushState("/cn/iphone/apps")` → 落在 App 页（应为 `/gb/iphone/apps`）
- 在 App 页 `pushState("/cn/iphone/music")` → 同样被弹回 App 页

用户表现为：在 App 页点任何分类导航都「没反应/被弹回原地」。

修复语义（`guard.js`）：`pendingAppUrl` 只在弹回的是**同一个 App** 时使用（比较去掉国家前缀后的 pathname）；其他路由一律只换国家前缀、保留自身路径。

**连带修正 6 处固化旧行为的单测断言**（us / clickedAppNavigation / popstate / location.assign / jp / restoredAppPath，以及循环保护用例改用「同一个 App」才能触发计数）。

### 缺陷 2：manifest host_permissions 缺域（静默失败）

`background.js` 会清理 `apple.com` / `itunes.apple.com` 上的 `geo`、`itspod`，但 manifest 只声明了 `apps.apple.com` 与 `fanqienovel.com`。真实运行时这些操作被拒：`No host permissions for cookies at url`，且被 `Promise.allSettled` 静默吞掉。

单测的假 chrome 不校验权限，永远发现不了。已补 `https://itunes.apple.com/*`、`https://apple.com/*`，并加了一条断言：background.js 里清理的每个域名都必须在 host_permissions 中。

### 顺带修的测试脆弱点

`puppeteer-test.mjs` 原来固定 `wait(1200)` 后就断言 SW target 存在；MV3 worker 懒启动实际需约 3 秒，导致偶发「extension service worker should be running」。改为最多 10 秒轮询。

### 排查方法论（可复用）

单测/浏览器套件全绿 **不等于** 功能正常。有效手段是写一次性探针脚本，用 puppeteer 加载真实扩展打真实站点，覆盖套件没覆盖的用户路径（冷启动直落 App 页、geo=CN 模拟国内 IP、跨域 cookie 操作、多标签页）。本次两个缺陷都是探针抓到的，套件全绿也照样漏。

环境提示：`npx --no-install puppeteer browsers install chrome` 装的是 Chrome 150（`C:\Users\Administrator\.cache\puppeteer\chrome\win64-150.0.7871.24\chrome-win64\chrome.exe`）。

## 第二轮：用户反馈「链接显示非 CN，但内容是 CN 内容」

第一轮修的是**地址栏**（URL 显示），用户真正报的是**内容**。两者是不同的失效维度。

### 关键前提：测试机出口 IP 是日本东京（G-Core Labs），不是中国

这是第一轮全部测试都漏掉方向的原因——日本 IP 下 Apple 不做 302 到 /cn/，症状根本不出现。**判断此类问题前必须先确认出口 IP 归属地。**

### 决定性发现：~~`geo` cookie 已完全失效~~（⚠️ 此结论的实验有设计缺陷，见第五轮补充）

> **第五轮更正**：这个实验全部跑在**日本出口**上——而日本出口下无论带什么 cookie 都返回 200，实验对「坏出口下 geo 是否有效」**零区分度**。「geo 失效」仅在好出口下成立（那里本来就无效），**从未在坏出口下验证过**。正在补测。

curl 实测同一 URL `/gb/app/facebook/id284882215`：

| 请求 | storefront | lang |
|---|---|---|
| 无 geo cookie | `gb` | `en-GB` |
| `geo=GB` | `gb` | `en-GB` |
| `geo=CN` | **`gb`** | **`en-GB`** |
| 路径换成 `/cn/` | `cn` | `zh-Hans-CN` |
| 路径换成 `/jp/` | `jp` | `ja` |
| 无前缀路径 | 301 → IP 推导的 `/us/` | — |

**Apple 现在按 URL 路径决定内容，`geo` cookie 完全不参与。** 整个扩展的 cookie 机制已失去作用（不必立刻重构，但不能再把它当作有效手段）。

### 真正的根因：per-tab 重写规则漏了 main_frame

`buildCountryRewriteRule` 原本只有 `["xmlhttprequest", "sub_frame"]`。Apple 的 storefront 自校正以**主文档级** `/cn/` 导航形式到达，DNR 漏过 → 真的下载了 CN 页面 → `guard.js` 只能改地址栏，改不了已下载的 HTML → 「URL 是 /gb/，内容是中文」。

修复：加上 `main_frame`。验证证据：
- `testMatchOutcome({type:"main_frame"})` → `matchedRules: [{ruleId:10000}]`
- 标签页内实际出现 `/cn/iphone/today` 并被改写回 `/gb/`
- `lang: "en-GB"`、CJK 仅 2 字

### 测试盲区（这次栽跟头的地方）

`test.mjs:1141` 与 `puppeteer-test.mjs:121` 都只断言了 `xmlhttprequest`，其中后者还**显式把 main_frame 排除**（`deepEqual(types.sort(), ["sub_frame","xmlhttprequest"])`），把缺陷固化成了期望。两处都已补断言，并已验证「回退修复 → 测试立刻失败」，确认断言有牙齿。

### 方法论教训

1. 先确认**出口 IP**，否则测的是错误的场景。
2. **URL 对 ≠ 内容对**。要断言 `document.documentElement.lang` 和正文字符分布，不能只看 URL/cookie。
3. 改动 `resourceTypes` 这类「缩小拦截面」的修改，必须同步更新固化旧值的断言，否则测试会绿着放过回归。
4. 无法获得中国 IP 时，可用 CDP `Fetch.enable` 拦截主文档请求并返回 302 到 `/cn/`，确定性复现大陆 IP 行为。

## 第三轮：用真实浏览器 + CDP 实测（用户环境）

### 当时的（错误）判断：Clash 分流节点

用户的机器跑着 **Clash Verge / mihomo**（fake-ip 模式 + 系统代理 + TUN）：

- `apps.apple.com` DNS 解析为 **`198.18.1.188`**（RFC 2544 保留段，Clash fake-ip 特征）
- 配置 `profiles/*.yaml` 里 `DOMAIN-SUFFIX,apps.apple.com,YuShe` 的**优先级高于** `DOMAIN-SUFFIX,apple.com,DIRECT`
- 即 Apple 域名走代理组 `YuShe`，与其余流量出口不同

Apple 按**出口**判定 storefront。当 `YuShe` 选中的节点让 Apple 判定为大陆时，Apple 把 `/gb/...`、`/jp/...` 一律 302 到 `/cn`，内容是中文——**这就是用户报的「链接非 CN 但内容是 CN」**。

**铁证（同一台机器、同一份代码）**：

| 时间 | 结果 |
|---|---|
| 23:47 / 23:50 | 浏览器测试失败，Apple 强制 CN |
| 23:53 | 连 `a[href="/jp/iphone/apps"]` 都超时（页面里全是 `/cn/` 链接） |
| 23:55 | **38 秒通过**，Apple 配合返回 JP |

几分钟内自动翻转 ⇒ 代理节点切换（url-test 之类）导致，与扩展代码无关。

### 我上一轮的 `main_frame` 修复是错的，已撤销

加上 `main_frame` 后，Apple 的 `302 /gb → /cn` 与我们的 `307 /cn → /gb` 互相打架：

```
302 /gb/iphone/apps  -> /cn
301 /cn              -> /cn/iphone/today
307 /cn/iphone/today -> /gb/iphone/today   ← 我们的 DNR
302 /gb/iphone/today -> /cn                ← Apple 又打回
... 无限循环 → ERR_TOO_MANY_REDIRECTS
```

**硬报错比原来的「内容变中文」更糟。** 已撤销为 `["xmlhttprequest","sub_frame"]`，并在单测 + 浏览器测试里**反向锁定**（断言 main_frame 必须被排除），防止将来有人再加回来。

关键认知：**Apple 坚持时，浏览器端无法拿到非 CN 内容**——内容来自 Apple 服务器，`guard.js` 只能改地址栏，改不了已下载的 HTML。真正的杠杆是网络出口，不是扩展。

### 测试套件改动

- 新增**环境前置检查**：首个 GB 页面若正文是中文 / `/cn/` 链接占多数，直接以明确信息失败，指出「检查 `*.apple.com` 的代理分流」，而不是三步之后抛选择器超时。
- JP 切换断言改为「扩展自身不得产生多余跳转」（过滤 Apple 的 `/cn` 弹回），因为那是服务端行为。

### CDP 实测要点（复现用）

- 用户 Chrome 154，9222 端口。`/json/*` 端点返回 404 是正常现象（经 `chrome://inspect` 勾选开启的调试只暴露 WebSocket）。
- 真实调试路径在 `AppData/Local/Google/Chrome/User Data/DevToolsActivePort`（第二行是 wsPath）。
- 扩展 SW 平时休眠；**导航到 apps.apple.com 唤醒后立刻 `Target.getTargets` 找 `service_worker`** 才能附着读取 `chrome.runtime.getManifest()` 与 DNR 规则。
- `Network.getAllCookies` 需先在 page session 上 `Network.enable`，不能在浏览器级直接调。
- 环境有 `HTTP_PROXY=127.0.0.1:24024`，curl 访问 localhost 必须加 `--noproxy '*'`。

## 第四轮：用户明确「只会在启用代理的情况下使用 App Store」

即代理是固定前提，「改分流/关代理」不是可接受方案。因此我实测了唯一可能的**扩展侧**出路。

### `x-apple-store-front` 能强制 storefront，但用于导航是死路

Apple **确实认**这个头，且能覆盖出口判定。实测（出口被判定为大陆时）：

| 请求 | 结果 |
|---|---|
| 无头，任意国家路径 或 无国家路径 | `302 -> /cn` |
| `x-apple-store-front: 143444-2,29` | **`200`**，载荷 `"storefront":{"cc":"GB","id":"143444"}` |
| `143444-1,29` | `400`（格式敏感，`<id>-<n>,<n>`） |

已确认 ID：**GB=143444，US=143441**。

但**不能用在 main_frame**：

| 请求 | 带头结果 |
|---|---|
| App 页 `/gb/app/...` | `200` 但返回 **JSON**（`storePlatformData`），不是 SPA 外壳 |
| 分类页 `/gb/iphone/today` | **`404`** |

带头会让 Apple 切到「store front API 模式」，标签页永远拿不到 HTML 页面。只能用于 XHR/sub_frame，而 SPA 的 API 路径本身已含 `/gb/`，加了也没有增益。

**结论：出口判定导致的 CN 弹回，扩展无法修复。** 唯一杠杆是网络出口。已在 AGENTS.md 写明，防止后人重新尝试这条路（或更糟——真的把它加到 main_frame 上）。

### 给用户的处置建议

Clash 里 `DOMAIN-SUFFIX,apps.apple.com,YuShe` 这条规则让它走了 `YuShe` 组。需要确保该组**不选中大陆节点**（或给 Apple 域名单独指定非大陆节点）。这是当前唯一能让扩展正常工作的方式。

## 第五轮：纠正——根因不是我说的代理规则（用户指出后复核）

用户指出「现在不是修复了吗，根本不是代理规则问题」。复核后确认**用户是对的，我错了**。

### 我犯的错：把推断当成了结论

我看到 Clash 在运行 + fake-ip 解析 + 配置里 Apple 域名的规则优先级，就推断「Apple 看到大陆出口」。**但我从未测到「Apple 看到的出口是大陆」**——尝试测时 `api.ip.sb` 返回 403，我却在没测到的情况下把推断写成了结论，还写进了 AGENTS.md 和给用户的建议里。

### 对照实验（决定性）

同一台机器、同一网络路径、同一时间窗口：
- **裸 Chrome（不加载扩展）** → `/gb/iphone/today`：`lang=en-GB`、80 个 `/gb/` 链接、0 个 `/cn/`、无弹回
- **带扩展 Chrome** → 完全相同的结果

**两者表现一致 ⇒ 扩展不是 CN 内容的原因。** 若真是代理/环境问题，裸 Chrome 会一起中招。

### 补充事实

- 出口 IP 在弹回前后**都是同一个** `31.223.184.121`（日本）。弹回时我拿到 403 没能验证，滚动窗口结束后仍是同一 IP。
- 测试套件在同一环境里：23:55 通过(38s) → 00:08 失败 → 00:10 通过(38s)。**同一份代码、同一台机器，分钟级翻转。**
- 现在 curl 对所有国家路径均返回 200。

### 修正后的结论

1. **弹回是间歇的、真实的，但触发条件未查明。** 不要写成因，除非测到。
2. **它不是扩展造成的**（裸 Chrome 对照已证）。
3. fake-ip / Clash 只是「线索」：它证明链路上有透明代理，**但不能推出出口归属**。
4. 已修正 AGENTS.md：删掉未经证实的代理归因，改为记录对照实验方法与「勿凭猜测填原因」。

### 仍然成立的两个结论

- `main_frame` 会造成 `ERR_TOO_MANY_REDIRECTS` 死循环（实测复现），必须排除——这是本轮唯一真正修掉的回归，且是**我自己引入的**。
- Apple 弹回后扩展无法恢复内容（HTML 来自 Apple 服务器）；`x-apple-store-front` 头是死路（分类页 404、App 页返回 JSON）。

### 教训

**「环境里有可疑组件」不等于「它就是原因」。** 必须有对照实验（本次：同机裸 Chrome vs 带扩展），否则就是把推断当结论，还可能误导用户去改无关配置。这次的代价是我给出了一个错误的排障方向。

## 第六轮：弹回根因查明（有完整证据链，不再猜）

监视器采样 109 次 + mihomo 内核日志交叉验证，终于把间歇弹回钉死：

### 根因：节点落地 IP 被 Apple 间歇性误判为 CN

**证据链**：
1. mihomo 内核日志：`apps.apple.com` 的 TCP 连接**全程**匹配 `YuShe[日本 01]`，包括弹回窗口正中（08:05-08:08）——分流规则从未变化、从未切换节点
2. 出口 IP 恒定：31.223.184.121（G-Core Labs Tokyo），弹回前后、弹回期间、恢复后全是同一个
3. 节点架构（订阅文件）：用户 → 国内中转（117.149.251.176，中国移动）→ G-Core Tokyo 落地 → Apple
4. mihomo 在弹回窗口内记录 `failed to create session: dial tcp 117.149.251.176:23031`——国内中转层在抖动，但落地 IP 不变
5. curl（沙箱独立出口）与 Chrome（Clash → 日本 01）**同步**弹回——因为两者落地是同一个 IP
6. 裸 Chrome 与带扩展 Chrome 行为一致

**判定**：G-Core Labs 是在中国有合资业务的 CDN/边缘云厂商，其 IP 段（31.223.x.x）在 GeoIP 数据库中归属混乱。Apple 的边缘节点对这个 IP 的判定在「日本」和「中国」之间摇摆，每次持续几分钟。判定为 CN 时，服务端把所有国家路径 302 到 /cn。

### 用户两个判断的最终裁定

| 用户的说法 | 裁定 |
|---|---|
| 「不是代理规则问题」 | ✅ **对**。分流规则全程稳定正确，从未变化 |
| 「用户只在启用代理时用 App Store」 | ✅ 关键前提。这排除了「不用代理」的方案，把问题收敛到「节点落地 IP 质量」 |

### 解决方案（一次性，无需改扩展）

换一个**落地 IP 的 GeoIP 归属稳定**的节点——比如香港 02、美国 01，避开 G-Core Tokyo 落地的节点。换完扩展即刻正常工作。

### 剩余的扩展侧真 bug（与本根因独立，均已修复）

1. `pendingAppUrl` 全局劫持（第一轮）——SPA 导航被拖回旧 App 页
2. `host_permissions` 缺失（第一轮）——跨域 cookie 清理静默失败
3. `main_frame` 死循环（第三轮，**我自己引入的**）——已撤销并反向锁定
4. 测试环境前置诊断（第五轮）——红绿灯不再骗人
5. DRY 重构（第六轮）——测试辅助函数收敛

### 附加数据点（08:38-08:43，结论收尾后当场复验）

- 08:41:06 浏览器测试失败（JP 切换后正文无 `/jp/` 链接 = Apple 又发 CN 内容）
- 08:43 curl 同一 URL、同一 Clash 路径 → **200 恢复**，出口仍为 31.223.184.121
- 又一个「几分钟窗口、随机翻转」周期，与根因判定吻合

**弹回窗口完整记录**：07:47-07:53 ❌ → 07:55 ✅ → 07:59-08:09 ❌ → 08:10 ✅ → 08:41 ❌ → 08:43 ✅。红绿交替与 Apple 端 GeoIP 判定摇摆一一对应，扩展代码全程未变。
